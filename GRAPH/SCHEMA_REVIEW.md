# GRAPH SCHEMA REVIEW

**Status:** Advisory. This document is Level-5 in the authority hierarchy (MASTER_CONTEXT.md Article I), same as [SCHEMA.md](SCHEMA.md) itself — it reviews that document against [VISION.md](../VISION.md), [MASTER_CONTEXT.md](../MASTER_CONTEXT.md), and [ROADMAP.md](../ROADMAP.md), but it does not modify SCHEMA.md. Every finding below is a recommendation; none become binding until explicitly incorporated into SCHEMA.md in a separate step. This review does not implement anything, choose a storage backend, or write code — consistent with Scientific Constitution Before Code (VISION.md Article IX).

**Method:** each finding cites the SCHEMA.md section it concerns, the constitutional article it's evaluated against, a severity (`Critical` / `Moderate` / `Minor`), and a recommendation. Findings that would require a constitutional amendment (rather than a SCHEMA.md edit) are marked as such.

## 1. Missing Biological Domains

*Checked against: ROADMAP.md Article II (Phase 1 entity list); MASTER_CONTEXT.md Article IV (must absorb new data types without rewrite).*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| D1 | **Epigenetics has no entity type.** DNA methylation, histone modification, and chromatin state are a distinct, high-value biological domain (gene regulation, cancer biology) not covered by `biolink:NucleicAcidEntity`/`Transcript`. Not named in ROADMAP Article II either, but genomes/genes without regulatory state are an incomplete "universal biological memory." | Moderate | Add `biolink:Genome`-scoped epigenetic feature types (or the Biolink `EpigenomicEntity` category if present in the pinned version) before Phase 1 is considered structurally complete for genomics. |
| D2 | **No entity for gene/protein expression data.** SCHEMA.md lists an `expressed_in` predicate but no entity representing a quantitative expression measurement (tissue, level, condition). Without it, "expressed in liver at level X under condition Y" cannot be represented — it collapses to a boolean edge. | Moderate | Add an expression-measurement association type carrying tissue/condition/quantity, distinct from the boolean `expressed_in` predicate. |
| D3 | **No entity for molecular function / biochemical reactions.** Pathway (`biolink:Pathway`) is present, but GO Molecular Function and reaction/metabolite-level detail (enzyme kinetics, substrates, products) are not — "biological pathways" in ROADMAP Article II is currently only representable at the coarse pathway level, not the reaction level within it. | Moderate | Add `biolink:MolecularActivity` / reaction-level types, sourced from GO-MF, as a Phase 1 extension before pathway data is ingested in depth. |
| D4 | **No macromolecular complex type.** Two or more proteins forming a functional complex (ribosome, spliceosome) has no entity — only pairwise `interacts_with` edges, which can't represent an N-ary complex as a single addressable thing. | Minor | Add `biolink:MacromolecularComplex` (already in Biolink) as a Phase 1 entity type. |
| D5 | **No population/cohort-level entity.** Genomes and mutations are modeled per-entity, but population-scale data (allele frequency across a cohort, GWAS-style association) has no representation distinct from a single `SequenceVariant`. "Genomes" in ROADMAP Article II plausibly includes population genomics, which needs this. | Moderate | Add a population/cohort entity (Biolink has `PopulationOfIndividualOrganisms`, already used for `xerdna:MicrobialCommunity` — extend the same pattern for human/model-organism cohorts) and an allele-frequency-bearing association type. |
| D6 | **No gene–environment interaction modeling.** Environmental/exposure factors (diet, toxins, environment) that interact with genetic variants are absent from both entity types and predicates. This is a major biology domain (GxE) with no current path into the graph. | Minor | Flag as a deliberate Phase 1 scope decision if intentional, or add an `ExposureEvent`/environmental-factor entity type if not — currently the omission isn't stated as a choice anywhere, which is itself the gap. |

## 2. Weak Evidence Handling

*Checked against: VISION.md Article IV (Evidence Principles), Article VIII (tiers must not blur); MASTER_CONTEXT.md Article II Rule 1.*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| E1 | **No ingestion-time rubric for assigning `established_evidence`.** The Evidence Model says only "structured ingestion from a recognized authoritative source" may set this tier, but doesn't define what makes a source "authoritative" versus merely convenient. Real sources mix curation levels internally (e.g., manually reviewed vs. automatically annotated records within the same database) — without a rubric, two ingestion engineers could tier the same kind of record differently, silently violating VISION.md Article VIII. | **Critical** | Before any ingestion connector is written, define a per-source tiering rubric (e.g., "manually curated + peer-reviewed → established_evidence; automatically annotated within the same DB → computational_prediction") as part of each source's own design document, with SCHEMA.md stating this rubric is mandatory, not optional, for every new source. |
| E2 | **No handling for causal vs. correlational claims.** A GWAS association ("variant statistically associated with trait") is peer-reviewed and published, but asserting causation from it is a different, stronger claim. The Evidence Model doesn't distinguish "the association was observed and published" (established evidence about a correlation) from "the variant causes the trait" (a much stronger claim that may only be a hypothesis). Collapsing these into one `established_evidence` edge risks exactly the false confidence VISION.md Article VIII exists to prevent. | **Critical** | Add a qualifier (Biolink supports predicate qualifiers) distinguishing observed statistical association from asserted causation, and require correlational findings to default to a weaker predicate (`correlated_with`, not `causes`) unless the source itself asserts and supports causation. |
| E3 | **No retraction/supersession lifecycle.** The Provenance Model has `retrieved_at` but no `status` (`active` / `retracted` / `superseded_by`). Papers get retracted and databases get corrected; an `established_evidence` record ingested before a retraction has no mechanism to reflect that its source is no longer valid. | Moderate | Add a provenance lifecycle status field, and a scheduled or event-driven recheck process (design, not implementation, at this stage) for `established_evidence` records against source retraction feeds. |
| E4 | **Conflicting `established_evidence` is not explicitly anticipated.** ROADMAP.md Article III (Phase 2) expects the reasoning engine to find "conflicting evidence between sources," but SCHEMA.md never states that two contradictory `established_evidence` edges between the same nodes are an expected, valid graph state (as opposed to a data error to be resolved at ingestion). Left unstated, a future ingestion implementation might wrongly try to "resolve" conflicts by picking one source over another, destroying the conflict signal Phase 2 needs. | Moderate | Add an explicit statement: contradictory `established_evidence` edges are valid and preserved, not deduplicated away — conflict resolution is Phase 2's job, not ingestion's. |

## 3. Unclear Hypothesis Boundaries

*Checked against: VISION.md Article V Rules 2–3; ROADMAP.md Article IV.*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| H1 | **No defined promotion path from `computational_prediction` to `research_hypothesis`.** A high-confidence prediction and a hypothesis are structurally distinct in SCHEMA.md, but nothing defines when (or whether) a prediction becomes eligible to be written up as a hypothesis, or who/what does the promoting. Without this, Phase 3 implementers could conflate "high-confidence prediction" with "hypothesis" inconsistently, quietly eroding the boundary VISION.md Article VIII requires to stay sharp. | **Critical** | Define the hand-off explicitly: a hypothesis may cite predictions as `supporting_evidence`, but a prediction never becomes a hypothesis by confidence threshold alone — only by an explicit reasoning step (Phase 2/3 process) that produces the required `claim`, `contradicting_evidence`, and `reasoning` fields. |
| H2 | **`claim` scope is ambiguous for multi-entity hypotheses.** The Hypothesis Model says a claim is "scoped to specific graph entities," which reads as pairwise (node-to-node), but real hypotheses often concern a subgraph or mechanism (e.g., "pathway A modulates disease B via intermediate C") involving three or more entities. | Moderate | Clarify that `claim` may reference an arbitrary set of graph entities/edges (a subgraph), not just a single pairwise relationship. |
| H3 | **No deduplication or identity model for hypotheses themselves.** The Entity Identity section solves this problem for biological entities but not for hypotheses. Once Phase 6 (Collective Intelligence) opens contribution to many researchers, near-duplicate hypotheses are inevitable, and there's currently no analog to `xerdna:possibly_same_as` for hypothesis records. | Moderate | Extend the identity-resolution pattern to hypotheses: near-duplicate hypotheses get a `xerdna:possibly_duplicate_of` relationship rather than silent merging or unchecked duplication. |
| H4 | **Terminal-looking `status` values aren't explicitly non-terminal.** `refuted` and `supported_by_experiment` read as end states, but VISION.md Article III says XERDNA is never "done," and science revisits settled questions. Nothing in the Hypothesis Model states that a `supported_by_experiment` hypothesis can later be reopened by new contradicting evidence. | Minor | Add an explicit statement that no `status` value is permanently terminal — any status can transition again given new `established_evidence`. |

## 4. Ontology Gaps

*Checked against: MASTER_CONTEXT.md Article IV, Article V Rule 4 (prefer standards).*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| O1 | **No pinned Biolink Model / OBO ontology versions.** SCHEMA.md adopts Biolink and OBO ontologies but names no version. Both evolve — Biolink has made backward-incompatible category changes across major versions, and GO/ChEBI/Mondo release on their own cadences. Without a pinned version and an explicit upgrade policy, historical graph data can silently drift out of sync with the vocabulary it claims to use. | **Critical** | Pin an explicit Biolink Model version and OBO release snapshot in SCHEMA.md, and define an upgrade policy (e.g., ontology version upgrades are themselves schema-level decisions requiring a rationale, per the Namespace Registry governance pattern already established). |
| O2 | **`method` in the Prediction Model is free text, not ontology-grounded.** This is inconsistent with Design Rule 1 (typed, never ad hoc) — an unstructured method name risks the same ungrounded-string sprawl the rest of the schema deliberately avoids, and undermines cross-source comparability of methods. | Moderate | Ground `method` in a controlled vocabulary (e.g., OBI — Ontology for Biomedical Investigations) where the method is a known assay/algorithm type, falling back to free text plus a flagged `ontology_gap: true` only when no term exists yet. |
| O3 | **No treatment of cross-namespace chemical identity granularity.** The xref strategy treats external IDs as interchangeable `(namespace, id)` pairs, but chemical identifiers (ChEBI, PubChem CID, InChIKey, DrugBank ID) frequently refer to different structural granularities of "the same" compound (parent compound vs. specific salt or stereoisomer) — a well-known cheminformatics hazard. Naively merging on any shared xref risks conflating distinct chemical entities. | Moderate | Add a chemical-identity-specific caveat to the Entity Identity section: chemical xrefs require a granularity check before merge, not just a namespace/ID match. |
| O4 | **No use of Biolink's qualifier system for directionality/polarity.** Relationship types are listed as simple predicates (e.g., `interacts_with`, `correlated_with`) without Biolink's qualifier slots (e.g., object-direction qualifier for "increases" vs. "decreases"). Losing directionality on regulatory relationships ("gene X upregulates gene Y" vs. an undirected association) is a significant expressiveness loss for a biological knowledge graph. | Moderate | Adopt Biolink's predicate + qualifier pattern explicitly in the Relationship Types section rather than bare predicates. |

## 5. Future Phase 2/3 Compatibility

*Checked against: ROADMAP.md Article III (Phase 2), Article IV (Phase 3).*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| P1 | **No representation for "checked, no evidence found."** VISION.md Article V Rule 5 states "absence of evidence is data," and ROADMAP.md Article III requires Phase 2 to find "research gaps — areas with surprisingly little evidence." But SCHEMA.md has no mechanism to record that a given entity-pair/relationship-type combination was actively checked and came up empty, versus simply never having been queried. Without this distinction, Phase 2 cannot tell a real gap from an unexplored area, which are different findings. | **Critical** | Define a "checked-absent" record type (or a reasoning-engine-owned index, forward-referenced here but designed in the Phase 2 spec) so gap-finding has data to work from starting in Phase 1, not retrofitted in Phase 2. |
| P2 | **No `Finding` entity for Phase 2 output.** ROADMAP.md Article III says Phase 2 produces "structured findings... always labeled by evidence tier," implying findings are themselves evidence-tiered graph objects, but SCHEMA.md defines no such type — only raw entities/edges and, separately, hypotheses. The Hypothesis Model's `generated_by` field references "reasoning process" but not a concrete `Finding` record it derived from. | Moderate | Add a placeholder note (not a full design, since that's Phase 2's document) acknowledging a `Finding` type will sit between raw graph data and `research_hypothesis`, so Phase 3's design isn't forced to retrofit it. |
| P3 | **No support for tracking graph staleness for Phase 5.** ROADMAP.md Article VI (Phase 5 — Autonomous Scientist) requires continuously updating the graph as literature is read. The Provenance Model's `retrieved_at` records when a fact entered the graph, but nothing tracks whether the *source* has since changed — directly related to Finding E3 (retraction/supersession) above, and a blocker for Phase 5 functioning correctly when it arrives. | Moderate | Same recommendation as E3 — a provenance lifecycle status is a prerequisite for Phase 5, not just a Phase 1 nicety. |

## 6. Risks to the 2,000-Phase Rule

*Checked against: VISION.md Article IX; MASTER_CONTEXT.md Article IV.*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| R1 | **No schema-version tag on ingested records.** As SCHEMA.md itself is amended over time (as this review's own recommendations demonstrate it will be), previously-ingested records have no field recording which version of the schema they were created under. A future structural change (e.g., a newly mandatory field) has no way to distinguish "old record, valid under an earlier schema" from "malformed record." Over hundreds of future phases, this is close to guaranteed to cause silent data-quality decay. | **Critical** | Add a `schema_version` field to every node and edge, incremented whenever SCHEMA.md changes in a structurally-relevant way (new required fields, changed tier semantics). |
| R2 | **No entity split/merge lineage.** The Entity Identity section handles duplicate-detection (two source records, one real entity) but not the reverse and more disruptive case: a single canonical entity later found to actually be two distinct entities (common in genomics as genome assemblies and gene models are revised), or two canonical entities later found to be one. There is no lineage mechanism to preserve history through a split or merge. Given genes/genomes are the most central Phase 1 entity type and gene-model revisions are routine, this will happen repeatedly across the platform's lifetime. | **Critical** | Design a split/merge lineage mechanism (e.g., `xerdna:split_into` / `xerdna:merged_from` relationships preserving both the old and new canonical IDs) before large-scale gene/genome ingestion begins. |
| R3 | **Namespace Registry governance doesn't anticipate multi-contributor scale.** The current governance ("schema-level decision... doesn't require Article III amendment... requires a recorded rationale") is reasonable for a single architect but has no defined review/approval path for when Phase 6 (Collective Intelligence) opens contribution broadly. Without a stated escalation process, namespace sprawl could reappear gradually — the exact failure mode the registry exists to prevent, just on a longer timescale. | Moderate | Add a forward-looking note that registry governance itself will need revisiting (not necessarily solving now) before Phase 6, flagging it explicitly rather than leaving a silent gap. |
| R4 | **Reliance on an external, still-evolving standard (Biolink) has no stated migration strategy.** Related to O1, but distinct in kind: O1 is about version drift within normal operation; this is about the long-term risk that Biolink itself could be abandoned, forked, or restructured in ways XERDNA can't control, given the platform is meant to outlast any single external dependency (VISION.md Article IX). | Moderate | Not urgent to resolve now, but SCHEMA.md should state the abstraction boundary explicitly: XERDNA's own `xerdna:` canonical IDs and internal type hierarchy are the durable layer; Biolink/OBO mappings are a translation layer that could, in principle, be re-pointed at a successor standard without renumbering XERDNA's own entities. This is likely already implied by the design but is worth stating outright as insurance. |

---

## Summary

Of 25 findings across all six checks, **7 are Critical** and should be resolved, or explicitly deferred with rationale, before Phase 1 ingestion design begins in `DATA/`:

- **E1** — no rubric for assigning `established_evidence` at ingestion.
- **E2** — no distinction between correlational and causal claims.
- **H1** — no defined boundary between prediction and hypothesis promotion.
- **O1** — no pinned ontology versions.
- **P1** — no representation for "checked, found nothing" (blocks Phase 2 gap-finding).
- **R1** — no schema-version tagging on records.
- **R2** — no entity split/merge lineage.

The remaining 18 findings (Moderate/Minor) don't block Phase 1 conceptual work but should be tracked so they aren't silently dropped.

**This review recommends; it does not amend SCHEMA.md.** Per Scientific Constitution Before Code (VISION.md Article IX) and MASTER_CONTEXT.md Article VII (Decision Principles), each accepted recommendation should be applied to SCHEMA.md as an explicit, traceable edit — not silently — before Phase 1 is considered ready to hand off to `DATA/` ingestion design.
