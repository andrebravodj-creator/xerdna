# PHASE 002 REVIEW

**Status:** Advisory. This document is the Review stage of the governance pipeline (MASTER_CONTEXT.md Article XII, stage 3), reviewing [DOCS/PHASE_002_DESIGN.md](PHASE_002_DESIGN.md) against VISION.md, MASTER_CONTEXT.md, ROADMAP.md, GRAPH/SCHEMA.md, DOCS/PHASE_001_FREEZE.md, and DOCS/IMPLEMENTATION_POLICY.md. It does not modify the design document. Every finding below is a recommendation; none become binding until explicitly triaged into a Decision-stage document, the same discipline GRAPH/SCHEMA_REVIEW.md was held to before GRAPH/SCHEMA_DECISIONS.md existed. This review does not write code and does not implement anything.

**A limitation of this review, stated rather than left implicit:** this review was produced by the same author as the design it reviews. DOCS/IMPLEMENTATION_POLICY.md Section 4 Rule 1 states "no implementer approves their own work's constitutional compliance" — a principle written for post-implementation review, but whose underlying reasoning (independence of judgment) applies here too. Where Phase 001's second audit pass explicitly reset its own assumptions rather than trusting the first pass's rigor, this review has tried to do the same against its own design — but a future, genuinely independent pass (human or a differently-scoped agent) remains advisable before Implementation begins, and this limitation is recorded here so it isn't silently forgotten.

**Method:** each finding cites the section of PHASE_002_DESIGN.md it concerns, the document/article it's evaluated against, a severity (`Critical` / `Moderate` / `Minor`, matching GRAPH/SCHEMA_REVIEW.md's convention for this stage), and a recommendation.

## 2. Scientific Integrity Risks

*Checked against: VISION.md Article IV (Evidence Principles), Article VIII (Scientific Integrity as Supreme Constraint); GRAPH/SCHEMA.md's Evidence Model, E1, E2.*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| SI1 | **The "small local allow-list of sources" (Section 5.2) is presented as standing in for E1's per-source tiering rubric, but the two are not equivalent instruments.** E1 requires a rubric distinguishing tiers *within* a source (e.g., manually-curated vs. automatically-annotated records in the same database); a flat allow-list of trusted source *names* only distinguishes *between* sources. Describing the allow-list as standing in for the rubric risks setting a precedent — once real `DATA/` connectors are built — that a source-level allow-list satisfies E1, when E1 explicitly requires finer granularity. | Moderate | Add an explicit caveat: this allow-list is a scope simplification valid only because the prototype's seed data has no intra-source tier variation to speak of, and does not set precedent for any real ingestion connector, which must still produce a real per-source rubric per E1. |
| SI2 | **`source_asserts_causation` (Section 4.3, enforcing E2) is a self-declared boolean with no truthfulness safeguard**, unlike the parallel treatment Anti-Hallucination Rule 4 receives (Section 6, row 4), where an unverifiable claim honestly defaults to `not_checked` rather than being trusted at face value. E2 and Rule 4 are structurally the same kind of problem — "a claim this prototype cannot independently verify" — but are held to different standards of rigor in this design. | Moderate | Apply the same honest-deferral pattern used for Rule 4: require the flag to reference the specific source passage asserting causation (mirroring Rule 2's `source_span`), not just a boolean, so the claim is at least inspectable even if not independently verified. |
| SI3 | **`primary_knowledge_source` / `aggregator_knowledge_source` value format is unspecified.** GRAPH/SCHEMA.md's Provenance Model and Foundational Choice section both use the `infores:` CURIE convention (e.g. `infores:uniprot`) for these exact fields, and the recently-applied v1.2 fix to the `biolink:InformationResource` row explicitly reinforces that sources are represented via `infores:` CURIEs on these slots, not as freestanding node categories. The design never states seed data must follow this convention, risking ad hoc, inconsistent source-naming the moment more than one contributor writes seed rows. | Moderate | State explicitly that `primary_knowledge_source`/`aggregator_knowledge_source` values follow the `infores:` CURIE convention, carrying forward the B2 resolution rather than leaving it unstated. |

## 3. Missing Enforcement Points

*Checked against: GRAPH/SCHEMA.md's Hypothesis Model, Provenance Model (E3), Schema Versioning (R1), Namespace Registry (B4).*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| MEP1 | **The Hypothesis Model's own established-evidence mechanism has no storage/gate representation.** GRAPH/SCHEMA.md states "`status` transitions into `refuted` or `supported_by_experiment` are themselves evidence-tier `established_evidence` events" — a *second*, distinct pathway to `established_evidence`, alongside the Prediction Model's `promoted_from` link (Section 5.3). The design only models the prediction-promotion pathway. `promoted_from`'s type (Section 4.3: "Optional foreign key to another `associations.id`") is also unrestricted as to which tier it may point at, meaning nothing in the design prevents it from pointing at a `research_hypothesis` record — conflating two mechanisms GRAPH/SCHEMA.md treats as distinct. | **Critical** | Add a second, explicit mechanism for hypothesis resolution (e.g., a hypothesis `status` transition to `supported_by_experiment`/`refuted` must itself trigger insertion of a linked `established_evidence` record, structurally separate from `promoted_from`), and restrict `promoted_from` to only reference `computational_prediction`-tier records. |
| MEP2 | **No test or seed row exercises the `established_evidence` source allow-list's rejection path.** Section 5.2 asserts the allow-list gate; Section 7's seed data doesn't include an attempted-and-rejected off-allow-list source, and Section 8's Test Matrix has no corresponding test. The mechanism is asserted but never proven to work. | Moderate | Add a seed/test case: an `established_evidence` insert attempted with a source not on the allow-list, expected to be rejected — mirroring how T8 already proves the `causes`-without-source-support rejection. |
| MEP3 | **`status` (E3: `active`/`retracted`/`superseded_by:<id>`) has no gate-level validation of its value set, and no test.** Section 4.1/4.3 declare the field required with a default, but nothing constrains it to the three valid forms, and nothing checks that a `superseded_by` value references a real, existing record. | Moderate | Add a gate check restricting `status` to the three valid forms (with `superseded_by:<id>` validated against existing IDs), and a corresponding test. |
| MEP4 | **`schema_version` is not stated to be immutable post-insert**, unlike `evidence_tier` and `xerdna_id` (Section 4.1, explicitly called out as immutable). R1's entire purpose — letting a future reader distinguish "valid under an earlier schema" from "malformed" — depends on this field never changing after the fact once set. | Moderate | State `schema_version` is immutable at insert, with the same two-layer (application + storage) enforcement already specified for `evidence_tier` in Section 5.3. |
| MEP5 | **T15 (Namespace Registry enforcement) has no corresponding seed data.** Section 7's seed data uses only bare Biolink categories and predicates (`biolink:Gene`, `biolink:interacts_with`, etc.) — none are `xerdna:`-namespaced. T15 asserts "`xerdna:` prefix or predicate not present in `xerdna_namespace_registry` cannot be used in any insert," but nothing in Section 7 uses an `xerdna:` term at all, so it's unclear what data this test would actually exercise (the split/merge seed item, Section 7's last bullet, implicitly uses `xerdna:split_into`/`xerdna:merged_from` per Section 4.8, but this connection is never made explicit). | Moderate | Either explicitly connect T15 to the split/merge seed row's use of `xerdna:split_into`, or add a standalone `xerdna:` term to Section 7's seed list specifically to exercise this test. |

## 4. Weak Validation Strategy

*Checked against: GRAPH/SCHEMA.md's Scientific Integrity Constraints, Anti-Hallucination Rules; IMPLEMENTATION_POLICY.md Section 5 (Validation), Section 6 (Testing).*

| # | Finding | Severity | Recommendation |
|---|---|---|---|
| WVS1 | **Section 6 introduces required fields never listed in Sections 4–5's canonical structure.** `source_span` (Rule 2), `resolution_status` (Rule 4), and the `basis` field for qualitative confidence (Rule 6) are all described in Section 6 as enforcement mechanisms, but none appear in Section 4's field tables (`associations`, `confidence`) or Section 5's gate-check descriptions. An implementer building strictly from Sections 4–5 — the sections that actually define storage structure and gate logic — would not discover these fields exist, and Section 6's claims would not hold on delivery. This is the review's most structurally significant finding: it means the design's own sections don't agree with each other about what the schema contains. | **Critical** | Add `source_span`, `resolution_status`, and `basis` to the appropriate Section 4 field tables and Section 5 gate-check lists, so Sections 4–6 are drawn from one consistent field inventory rather than three partially-overlapping ones. |
| WVS2 | **The read-path guarantee (Section 2, T14) has no structural enforcement, unlike every write-path guarantee.** Every write-side rule in this design gets defense-in-depth (an application check plus an independent storage-layer constraint, per Section 5.3's pattern). The promise that reads always surface `evidence_tier` and `primary_knowledge_source` rests on a single, unenforced function — nothing prevents a second read path, added later (inevitable once Phase 2/3, Roadmap numbering, builds a reasoning engine on top of this storage layer), from omitting them. This is precisely the failure mode GRAPH/SCHEMA.md's Scientific Integrity Constraint 2 exists to prevent, and the design's protection against it is currently a stated intention, not a described mechanism. | Moderate | Describe a structural guarantee for reads analogous to the write-side one — e.g., a single canonical view/query layer that always joins tier and source, with no lower-level accessor exposed that could bypass it. |
| WVS3 | **SQLite-specific operational risks are unaddressed.** SQLite disables foreign-key enforcement by default per connection (`PRAGMA foreign_keys = ON` must be set explicitly) — several of the design's referential-integrity claims (`node_xrefs`, `associations.subject_id`/`object_id`, `entity_lineage`) silently depend on this being enabled, and the design doesn't say so. Separately, Section 5.3's "row-level constraint" language for immutability doesn't distinguish that SQLite requires a `BEFORE UPDATE` trigger for this (a `CHECK` constraint cannot compare old and new values across an update) — a real implementation-mechanism gap, not just a wording nitpick, since building the wrong mechanism would silently fail to enforce the guarantee. | Moderate | State explicitly that `PRAGMA foreign_keys = ON` is set on every connection, and that immutability is enforced via `BEFORE UPDATE` triggers specifically, not `CHECK` constraints. |
| WVS4 | **No Python version is pinned** ("Python 3" generically, Section 3) — inconsistent with this project's own established discipline (O1) of pinning versions explicitly for reproducibility, applied so far only to scientific vocabularies, not yet to the runtime this prototype depends on. | Minor | Pin a minimum Python version (e.g., "Python ≥ 3.10") explicitly. |

## Scientific Constitution Before Code — Explicit Check

**No violation found.** PHASE_002_DESIGN.md's own "Status" line and "Next Steps" section correctly state that the document does not authorize Implementation by itself, and no code has been written. Every finding above is a concern about the *rigor and completeness* of what is proposed for eventual implementation, not an instance of implementation preceding its constitutional authorization. The closest finding to this category is SI1 (the allow-list-as-rubric simplification), which is a risk that a *future* simplification could drift into an unauthorized workaround if not explicitly bounded now — not evidence that one has already occurred.

## Summary

Of 16 findings: **2 Critical**, **10 Moderate**, **4 Minor**.

- **MEP1** — the Hypothesis Model's own established-evidence mechanism is unmodeled, and `promoted_from` doesn't restrict which tier it may reference.
- **WVS1** — Section 6 introduces required fields (`source_span`, `resolution_status`, `basis`) that Sections 4–5's canonical structure never lists, meaning the document's own sections disagree with each other about what the schema contains.

These two should be resolved, or explicitly deferred with rationale, before this design proceeds to a Decision-stage triage. The remaining 14 findings don't block Decision-stage work but should be carried into it, the same way GRAPH/SCHEMA_REVIEW.md's Moderate/Minor findings were carried into GRAPH/SCHEMA_DECISIONS.md rather than silently dropped.

**This review recommends; it does not amend PHASE_002_DESIGN.md.** Per Scientific Constitution Before Code and MASTER_CONTEXT.md Article XII, each accepted recommendation should be applied as an explicit, traceable edit in a separate step — a Decision-stage document is the natural next stage, mirroring GRAPH/SCHEMA_DECISIONS.md's role for Phase 001.
