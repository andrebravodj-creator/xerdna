# MILESTONE 001 POSTMORTEM

**Status:** Governance record, not implementation. This document reviews everything built and every process step taken across Engineering Milestone 001 — and, where relevant, the governance cycle that preceded it (DOCS/PHASE_002_DESIGN.md through DOCS/MILESTONE_001_COMPLETION.md). It modifies no code and no other document. Per MASTER_CONTEXT.md Article XII, this is retrospective input to whatever Milestone 002 planning follows — it does not itself authorize, block, or reopen Milestone 001, which stands as validated and complete.

---

## What Went Well

- **The ten-stage governance pipeline (Article XII) was exercised end-to-end against real code for the first time, and held.** Every stage ran in order — Architecture, Review, Decision, Remediation, a final engineering-readiness check, Implementation, Validation — with no stage skipped and no document silently amended. This is the pipeline's first empirical test since its own ratification, and it worked.
- **The "smallest possible task" discipline was genuinely applied, not just stated.** Milestone 001 stayed to exactly six tasks and the seven named deliverables. The temptation to also build Section 5 (The Insertion Gate) — which would have made the milestone feel more "complete" — was explicitly named and resisted, both in the implementation plan and in the actual build.
- **Validation was real, not asserted.** Eighteen tests were written and actually run (twice — once normally, once with `-W error::ResourceWarning` to force any latent resource-handling defect to surface), not claimed to exist and trusted on faith. A ResourceWarning was found and fixed before the milestone was called complete, rather than shipped with a known, uninvestigated issue.
- **Honest reporting of gaps continued into engineering, not just design review.** The `aggregator_knowledge_source` omission, the Python-version mismatch with the host environment, and the deliberate exclusion of cross-table enforcement were all surfaced and recorded rather than smoothed over — the same discipline this project applied to ontology version-pinning (leaving ChEBI/SO honestly unpinned) carried through into code.
- **Traceability held at the field level, not just the document level.** Every column in `schema.sql` carries a comment tying it back to a specific PHASE_002_DESIGN.md subsection; every module docstring cites what it implements. A reviewer can walk from a `CHECK` constraint to the design line that required it without guessing.

## What Could Be Improved

- **Design review checked internal consistency but not cross-document consistency with GRAPH/SCHEMA.md itself.** The `aggregator_knowledge_source` gap survived two full Review/Decision/Remediation cycles (v1.1, v1.2) and a final engineering-readiness review — all of which checked PHASE_002_DESIGN.md against itself and against the constitution, but none of which did a field-by-field comparison against GRAPH/SCHEMA.md's own Provenance Model. It only surfaced when translating the design into literal DDL forced that comparison implicitly.
- **Environment readiness was discovered mid-build, not gated for in advance.** The design correctly pinned `Python >= 3.10` (WVS4), but nothing checked the actual host environment against that requirement until implementation began and the default `python3` turned out to be 3.9.6. No prior stage — Review, Decision, Remediation, or the engineering-readiness review — includes an environment-verification step, because none of them execute anything.
- **"Independent" review has not yet been literally independent, at any point in this project.** Every stage of both Phase 001 and Phase 002 — Architecture, Review, Decision, Audit, Remediation, Approval — has been conducted by the same underlying actor, even when explicitly reframed as a distinct "Board." This was named honestly (PHASE_002_REVIEW.md's own opening caveat; TG3 in PHASE_002_DECISIONS.md, DEFERRED rather than resolved) but has now persisted across an entire implementation cycle without being addressed, only re-acknowledged.
- **Test coverage is structurally sound but narrow.** All 18 tests are meaningful and none are speculative about not-yet-built logic — but they exercise only the single-row constraints this milestone actually implements, with no attempt yet to probe edge cases within that scope (e.g., a `superseded_by:<id>` value referencing a real-but-wrong-table ID, multiple simultaneous constraint violations in one insert, or unicode/edge-case string handling in required text fields).
- **No repeatable, automated way to re-run validation exists yet.** Tests were run manually via direct interpreter invocation. This is consistent with "zero infrastructure," but it means nothing currently prevents a future change from silently breaking Milestone 001's guarantees unless someone remembers to re-run the suite by hand.

## Technical Debt Introduced

- **No application-layer access exists.** Anyone using this database today has to hand-write raw SQL against `schema.sql`'s tables directly — fragile, and exactly the gap Section 5 (The Insertion Gate) exists to close. Deliberate and scoped, but it is debt: every day before Milestone 002 lands is a day this database is usable only in a way that bypasses the design's own safety model.
- **No schema-migration mechanism.** `schema.sql` uses `CREATE TABLE IF NOT EXISTS` throughout, which safely no-ops against an already-initialized database but cannot apply a structural change (e.g., adding the missing `aggregator_knowledge_source` column) to an existing one. There is currently no `ALTER TABLE` path, versioned migration script, or equivalent. This is fine while the database has never been used for anything but tests — it will not be fine the first time real data exists and the schema needs to change under it.
- **No CLI or runnable entry point.** The engine is importable but not operable — there is no `python -m GRAPH.engine` or equivalent that a user could invoke directly to initialize a database from the command line. Everything so far has been exercised only through test code.
- **Minor test-fixture duplication.** Several tests in `test_milestone_001.py` repeat the same multi-column `INSERT` statement boilerplate rather than sharing a fixture/factory helper. Harmless at 18 tests; would become a maintainability tax if the suite grows without addressing it.

## Architectural Debt Introduced

- **The schema looks more protective than it currently is.** All 9 tables and their single-row constraints are in place, which can visually read as "the safety model is built" — but the platform's most safety-critical rules (no-silent-promotion enforcement, the `promoted_from`/`resolved_by` tier restrictions, "no confidence row if `established_evidence`") exist only in the design document, not in code, until Milestone 002. A direct `INSERT` today can violate any of these with no resistance. This gap is intentional and documented, but it is real architectural debt in the sense that the artifact's appearance and its actual guarantees have diverged, and that divergence needs to stay visible until Milestone 002 closes it.
- **The read-path guarantee (WVS2's "single canonical query layer") is a design note, not yet an architectural fact.** No read API exists yet, so nothing has actually been built that could violate — or honor — the pattern. The debt is that the pattern's enforcement is still purely aspirational.
- **The namespace registry table exists but nothing checks it.** `xerdna_namespace_registry` is structurally present, but no code path currently verifies that a `predicate` or entity `category` used elsewhere is actually registered before use — that check belongs to the gate (T15), which doesn't exist yet.
- **Code and conceptual design documents now share a top-level folder (`GRAPH/`).** This was a deliberate, justified choice (TG1: extend rather than invent a new folder), but as the engine grows, `GRAPH/` will increasingly mix prose (`SCHEMA.md` and its governance chain) with a real Python package. Worth watching, not yet worth changing.

## Scientific Debt Introduced

- **No real (even prototype-scale) scientific data has touched this system yet.** Section 7's seed data — the 3 entity categories, 3 predicates, and the full promotion/resolution/split scenarios — was designed but not inserted this milestone. The schema's structural correctness is validated; its fitness for actually holding a real Biolink-typed record end-to-end is not yet demonstrated.
- **`aggregator_knowledge_source`'s absence on `associations` is not merely a cosmetic gap.** GRAPH/SCHEMA.md states this field exists specifically "so a broken or biased aggregator can be identified and audited later, not just the original source." That audit capability currently does not exist for edges — only for nodes. Until this is closed, any future association ingested through an aggregator has no place to record that fact.
- **ChEBI and SO remain unpinned**, carried forward unchanged from GRAPH/SCHEMA.md — not new debt from this milestone, but worth restating here because it becomes concretely relevant the moment a `DATA/` connector or seed row touches a chemical or sequence-feature entity, which Milestone 002's seed data (Section 7) will do for `biolink:Disease`/`Gene`/`Protein` only, not yet for anything ChEBI- or SO-dependent.

## Governance Observations

- **This was the pipeline's first real stress test, and it produced a positive signal: Article XII did not need a mid-cycle amendment to handle a real implementation.** The ten stages, as ratified, were sufficient in form for this milestone's scope.
- **The unresolved independence gap (see "What Could Be Improved," above) has now outlasted one full implementation cycle without a decision, only a deferral.** TG3 was DEFERRED at Decision-stage with the stated intent to "revisit explicitly at Phase 002's Approval stage" — that revisit did not produce a change, only a repeated acknowledgment. This pattern — naming a governance gap honestly, then deferring it again at the next checkpoint — is itself worth naming, since it risks becoming a standing exception rather than a genuinely tracked, closing item.
- **Governance overhead relative to code volume is very high at this stage** — this milestone produced roughly a dozen governance documents across its full cycle (design, review, decisions, remediation, readiness review, completion, and now this postmortem) against roughly 400 lines of actual code. This is defensible for a first-ever implementation establishing precedent for everything that follows, but MASTER_CONTEXT.md Article XII does not currently distinguish gate weight by change size or risk — every change, in principle, owes the same ten stages. Whether that should continue to hold uniformly, or whether routine/low-risk changes should eventually earn a lighter path without weakening it for load-bearing ones, is an open question this project has not yet had to answer, because Milestone 001 was unambiguously load-bearing (the first implementation ever).

## Lessons Learned

- **Translating a design into literal, executable structure is a review technique in its own right, not just an implementation step.** It found a real gap (`aggregator_knowledge_source`) that three prior document-level review passes did not. A cheap version of this — translating a representative slice of a design into pseudocode or DDL *before* formal Review begins — may be worth adopting as a standing practice, not a byproduct of implementation.
- **Splitting "schema creation" from "the insertion gate" into two milestones, decided during Milestone 001's own planning, was the right call.** It kept this milestone small, fully testable on its own terms, and free of any dependency on not-yet-built logic. The same split-by-natural-design-section approach is likely to serve Milestone 002 well if it, too, is broken down rather than treated as one monolithic unit.
- **A constraint that exists only in a design document and a constraint that has been mechanically demonstrated are different levels of confidence, and the gap between them is worth closing as early and cheaply as possible.** Verifying `checked_absent` has no `evidence_tier` column via schema introspection, rather than trusting the DDL source read, is a small example of a pattern worth repeating: wherever a design claims an absence or an impossibility, the test should demonstrate it structurally.
- **Naming a governance gap is not the same as closing it.** The review-independence issue has now been named three times (PHASE_002_REVIEW.md, PHASE_002_DECISIONS.md, and implicitly again here) without a concrete resolution. A lesson worth carrying forward explicitly: a DEFER with a stated revisit trigger needs the revisit to actually produce a decision, not another DEFER, or the mechanism degrades into a formality.

## Recommendations Before Milestone 002

1. **Close, or formally re-DEFER with a stated trigger, the `aggregator_knowledge_source` gap in PHASE_002_DESIGN.md** before Milestone 002's gate logic starts handling association provenance — this is the point at which the gap stops being latent and starts being load-bearing.
2. **Pin and document the verified execution environment explicitly** (e.g., record that `/opt/homebrew/bin/python3.11` is the confirmed interpreter for this project) rather than leaving it to be rediscovered the next time someone builds from a clean environment.
3. **Add a schema-migration strategy to the design before `schema.sql` changes again.** Right now there is no path from an existing, populated database to a structurally-changed one — only fresh creation. This should be resolved before it's needed under real data, not after.
4. **Make an explicit, non-deferred decision about review independence before Milestone 002's own Approval stage** — either state concretely what would satisfy it and commit to obtaining it, or state explicitly why it remains acceptable to proceed without it for now, with a harder, dated trigger for revisiting rather than an open-ended "at the next Approval."
5. **Consider, but do not yet decide, whether Article XII should scale its gate weight to change size and risk** — flagged here as a question for the constitutional layer, not resolved unilaterally by this postmortem.
6. **Insert Section 7's seed data early in Milestone 002**, ideally before or alongside the gate logic that will validate it, so real (if synthetic) records flow through the schema and surface any remaining structural surprises before the gate is fully built around assumptions that haven't yet been exercised.
7. **Add a minimal CLI entry point** (e.g. `python -m GRAPH.engine`) as part of Milestone 002 or a small addendum to it, so the engine becomes operable by a human directly, not only importable by test code.

No code was written or modified in producing this postmortem.
